# Switch 原生图形管理：0.57.0-native

这次接管的是游戏使用的整个 XDK 图形管理边界：设备、状态、资源、着色器、绘制提交、同步、显示与回调。原来的异步 Vulkan 渲染器继续负责真正的 GPU 工作。

```text
游戏 / 游戏内联的状态写入
            ↓
原生设备、资源、同步与提交管理
            ↓
现有异步 Vulkan 渲染器 → Switch GPU
```

## 替换范围

构建时直接移除 `0x003c5260..0x003d48a0` 范围内的 **226 个旧 XDK 图形函数体**。最终 Horizon 符号表中，这 226 个函数均为 60 字节的原生分发桥。没有保留原函数体作为回退路径。其余 45 个游戏编译单元沿用 0.56.25，并核对 SHA-256。

新的 100 个原生入口覆盖静态检查发现的全部 **86 个游戏对外调用目标、1022 条调用边**。旧库内部的 FIFO、Miniport 和中间管理函数，由新的设备及提交实现承担其职责，不逐个照搬。未实现的入口会停止并报告地址；静态检查与已执行场景不能证明所有尚未游玩的内容都正确。

游戏内联的状态写入仍保留 ABI 兼容的数据结构。这包括纹理和调色板绑定、引用计数、顶点流、矩阵、材质、常量、视口及屏幕偏移。它们直接供原生实现读取，不再触发旧库的图形管理流程。

主要代码：

- [native_device.inc](../../src/d3d/native_device.inc)：设备、资源及整个 API 边界。
- [hle.cpp](../../src/d3d/hle.cpp)：共享状态转换、绘制入口与严格的命令检查。
- [threaded.cpp](../../src/d3d/gpu/threaded.cpp)：批次围栏、资源及父表面等待、读回命令。
- [backend.cpp](../../src/d3d/vk/backend.cpp) 和 [readback.h](../../src/d3d/gpu/readback.h)：真正等待 GPU 后，把颜色、深度及模板结果写回游戏内存。
- [runtime.c](../../packaging/switch/runtime/runtime.c)：调用游戏堆分配器、保存回调寄存器、协作式 VBlank 等待。

**直接确认的因果路径**是：实际请求为一次刷新间隔，进入 Swap 时已经到达或超过原目标，原生实现将目标改为“当前 vblank + 1”，主动等待平均 14.07 ms，随后才提交。19.216 ms 的其余帧墙钟被扩展为 33.286 ms。等待期间 CPU 只用了 0.182 ms，绝大部分是停等。GPU 时间属于并行线程/设备，不能再加进这条帧墙钟分解。

具体例子为原生帧 2310：上次呈现的 vblank 为 3585，本次进入 Swap 时是 3586，原目标已到；原生层将目标改成 3587。该帧主动等待 13.485 ms，其余帧墙钟 19.733 ms，最终帧间隔 33.218 ms。日志的 deadline、进入等待时间、退出 vblank 与这一分支逐项对应。

资源等待是第二项需要处理的串行开销：扣除 Swap 等待期间 CPU 后，稳定窗口其余 CPU 约 14.804 ms；其余墙钟约 19.216 ms，相差约 4.412 ms，与资源等待 4.411 ms 基本吻合。`NativeDestroy -> Recorded::WaitResource -> ResourceBatch -> Wait` 是代码中的同步释放路径；`D3D_BlockOnResource` 也会调用同一等待。当前真机日志没有逐个记录资源类型和这两个调用来源，因此不能宣称已确定全部 7 次等待的资源身份。本机调用记录中显式 BlockOnResource 很少，释放临时表面是下一步优先审查的来源，而不是据此取消全部资源等待。

读回 B 请求为零，N 的 readback_calls 和 readback_wait_us 均为零；此场景的退步没有由新增颜色/深度读回路径触发。稳定窗口纹理上传均值约 0.0051 ms/帧，编译总计 84.845 ms / 1747 帧（约 0.0486 ms/帧），不能解释持续的 33.3 ms 帧间隔。采样 PC 的旁证为同一窗口 246 个有效游戏线程快照中，100 个位于 `svcSleepThread`、60 个位于 `svcWaitProcessWideKeyAtomic`；LR 只证明其直接来自 nanosleep / 条件变量等待，不据此编造更深调用栈，也不将这些墙钟抽样比例换算为 CPU 开销。

56 个存活战斗 T 样本中的独占墙钟：命令记录 2.272 ms、状态 API 0.890 ms、绘制前状态同步 0.686 ms、绘制 API 外壳 0.463 ms、内联命令解析 0.187 ms、着色器 API 0.125 ms。这些是抽样墙钟计时，不是函数 CPU 耗时；它们说明后续 CPU 优化可以集中在命令记录和状态转换，但修复 30 FPS 退步应先处理提交同步策略及资源生命周期造成的串行等待。

下一步修改应让迟到的帧及时提交，避免在 CPU 原生层补等一整次刷新；再审查临时资源释放能否按使用批次延后回收，保留 CPU 确实要读写仍在使用数据时的同步。19.216 ms 是这次运行扣除主动等待后的观测量，不能直接承诺新版本帧率；去掉等待后任务重叠、资源压力和显示队列都会变化，需复测确认。

## 0.57.2-fix：取消刷新点补等，修正表面视图释放

用户授权修复并允许取消垂直同步。原生 Swap 现在不再根据 `native_vblanks` 把迟到帧推到下一次刷新。它用独立的 60 FPS 上限维持轻负载场景的速度：距离上次提交不足 16.667 ms 时只等待剩余时间，已经超时就立即提交。游戏内部的 vblank 时钟、回调和显式 BlockUntilVerticalBlank 保持运行。显示消费者仍由 Switch 系统管理，不再用显示刷新相位阻塞游戏侧提交。新日志中 V 的 periods 和 retargeted 为零，剩余 wait_wall 是独立帧率上限的等待。

`NativeDestroy` 对带父纹理的表面视图只回收句柄，不再等待整批渲染或把仍存活的纹理数据标脏。命令录制已有独立的头部副本；Release/Unbind 会先处理父资源的引用，父纹理真的失去最后一个引用时仍执行原有安全等待。拥有独立存储的表面、纹理、顶点缓冲以及显式资源同步仍保留必要等待。

确定性限速测试覆盖 8/16/19/27/40 ms 持续帧负载、300 ms 加载停顿和恢复，迟到帧不会量化到更慢刷新周期。资源专项故意暂停异步渲染，验证临时视图释放不阻塞、调用者复用头部后仍能回放正确数据，以及最后一个父引用释放必须等待；拥有和借用的头部都通过，原有读回、可见性、Reset 和销毁专项也通过。

### 标题自动战斗演示退出

用户确认是标题画面不操作后自动播放的实机战斗。`error.log` 有两条相同错误：
`truncated native index push buffer: 0x8524c11c`。
停止路径是原生 RunPushBuffer 桥接进入 `hle.cpp::RunPushBuffer`，检测到包头声明的
参数字数大于 PushBuffer.Size 剩余空间，主动调用 `ngb_stop`。地址是推送缓冲区对象，
不是宿主崩溃 PC；尾部 rc=0 也不表示没有错误。

原始 error.log 未保存包头、偏移和数据，单凭错误行不能判断是哪种越界。
实验回放新增 `--attract`，不发送按键；主机构建可用 `--push-diagnostics`，
只在出错时保存包头和命令流。这些开关不改动已上传的 Switch 包。
第一轮 180 秒回放经过 5589 次 Swap、3698 个至少 250 绘制 API 的帧，未触发该错误；
第二轮计划 600 秒，在约 308 秒处复现，缓冲区对象同样为 **0x8524c11c**。
该轮结果为 FAIL，文件在 `attract-repro-02/`，不是通过了 600 秒验证。

捕获到 Common=0x00020001、Data=0x854f89e0、Size=AllocationSize=15320。
从偏移 0 到 15315 是完整的三角带：BEGIN(6)、2047+1774 个打包索引字、
一个单独索引、END(0)，共 7643 个索引。偏移 15316 的最后一个字为 `0x3fc38002`。
新解析器把它的位 18..28 当作 count=2032，但缓冲区只剩这一字，于是主动停止。

核对原游戏的 `D3DDevice_RunPushBuffer`（0x003CAFC0）可见其先取 `Size - 4`，
并把 `Data + Size - 4` 作为回跳位置；0x003CAF20 的回接辅助函数向该位置写入
返回 FIFO 的跳转字。这意味着最后一字是 XDK 管理的预留位置，**不是应当解析的绘制数据**。
其旧内容即使形似 CALL，也不能按真实的嵌套命令执行。根因是原生替换遗漏了这一 ABI 语义，
并非本次索引内容不完整；修复应恢复真实命令长度，继续对命令区做严格边界检查。

`packet-abi-probe.cpp` 从当前实际解析函数提取代码，以捕获数据做独立试验：
当前版本重现同样的 stop；采用 Size−4 后输出的 7643 个索引逐项一致，五种预留字取值
不改变输出；故意截断实际索引区仍触发边界错误。结果和捕获文件哈希保存在
`packet-abi-probe.json`。这只是独立解析试验，尚未修改正式解析行为、运行修复后的完整演示
或部署新包，不把它写成已完成修复验证。

处理顺序是先解决演示解析退出，再把日志写入移出显示线程并复测显示间隔；
随后预热/持久化实际用到的着色器与管线，继续降低常态游戏线程 CPU。
单独修改 FPS 显示算法或继续调整垂直同步，不能解决这三类问题。

常态 CPU 仍是另一条必要工作。本轮只读取、核验并分析数据，未修改或上传新运行包。

## 新材质首次使用：两个 PC 项目的源码对照与方案

本节仅记录源码检查和设计，不代表已实现或部署。检查的是本地版本：
`black-pc` c065917、`ngb-pc-native-port` 94bc250、`nxvk` c3abea1。
明细保存于 `native-xdk-perf-0.57.3/material-prewarm-review.json`。

`black-pc/loader/src/d3d/pshader.cpp::ps_host_shader` 在进程内缓存未命中时直接调用编译器，
`vshader.cpp::vs_host_shader` 也在第一次使用时翻译并编译；这份本地代码尚没有 port 的完整
持久化、发布种子和首次绘制预热流程，不能把两者都描述为已经完全解决冷启动卡顿。

port 的 `loader/src/d3d/host.cpp` 在创建设备时依次执行：读取缓存并创建着色器对象、
准备游戏自带顶点程序、贴图池和绘制缓冲、回放绘制状态。相关关键点为：

- `shader_cache.cpp::prewarm_shaders` 合并玩家缓存与随包种子，一次读入内存并创建 GPU 对象。
  `take_warm` 按字节码复用对象，避免不同源码得到同一字节码后又在绘制时重复创建。
- `vshader.cpp::vsh_seed_prewarm` 使用游戏文件中的位置和哈希准备游戏自带顶点程序。
- `drawwarm.cpp::drawwarm_replay` 在 16×16 的临时目标上按已知状态实际绘制，再等待完成，
  触发 D3D9 驱动推迟到首次 Draw 的内部编译，随后恢复状态并释放临时资源。
- 新编译结果和新状态保存在本地，下次启动也参与预热。生成工具有覆盖率核对，防止种子
  与当前生成器失配。文档中的 100% 是其已记录测试的覆盖率，不是全游戏证明。
- 当前随附二进制实际含 447 个着色器缓存条目、8493 个绘制状态、7 个顶点程序配方；
  README 旧小节中的数量对应之前版本。其测试记录涵盖标题、完整演示及第 1–4 章。
- 可选编译预算会让尚未编译完成的绘制暂时缺失，因此默认关闭；本次设计保持首次绘制完整。

Switch 当前机制已有两阶段 `Prewarm`：先创建模块，再创建完整 Vulkan 管线。
缺口主要在覆盖范围与缓存生命周期：随包 `opening-120.recipes` 是
`recipe-subset.py` 从**前 120 个原始演示帧**截取的记录，实际只有 118 个模块配方、167 个
管线组合；`.ngb-spirv` 含 99 条记录，按源码哈希去重后为 98 条。此前的检查日志明确结束于
`verified 120 original demo frames`，不能把它称作完整演示预热。
同时，当前 Switch 启动路径没有配置 `NGB_D3D_CACHE` / `NV2A_SHADER_CACHE`，
后续遇到的内容不会通过现有磁盘缓存机制参加下一次预热。

两种后端的适配区别：本地 NXVK 的 `vk_common_CreateGraphicsPipelines` 会调用
`vk_graphics_pipeline_compile_shaders`，再通过 NVK 的编译器生成并上传 GPU 程序。
因此完整 Vulkan 管线的提前创建是主要对应点；不能据 D3D9 的经验就认定还必须
逐条做空绘制。应单独验证管线预建后的首次 Draw 是否仍有额外准备开销，再决定是否补充
实际绘制预热。port 将 MSAA 状态归一化的做法也不能直接复制：当前 Vulkan `PipeKey`
包含采样数，已有 `WarmSamples` 应按实际设置准备相应变体。

建议将工作作为一套完整机制落实：

1. 用当前 Switch 渲染器的生成规则采集完整演示、Alma 及出魂、飞燕、UT 等效果所需配方，
   合并为发布资源，保留覆盖检查。PC 侧可生成匹配的 SPIR-V；port 的 D3D9 字节码不能直接使用。
2. 启动或加载阶段合并发布配方与玩家缓存，在 Switch 本机把所需模块和完整管线创建完成，
   游戏中直接复用。实测启动时长和内存成本，不能外推 port 在 PC 上的预热耗时。
3. 后续新内容保存配方、SPIR-V 和兼容本设备/驱动的管线缓存，并在下次启动预建。
   写盘移出实时绘制路径，校验生成器版本和驱动缓存兼容性。仅打开现有缓存目录仍会留下
   `CacheRecord`/`Compile` 中逐条 fflush 的停顿，需要一起处理。
4. 从空玩家缓存首次启动验证演示及目标战斗，检查目标内容运行时的未命中和创建次数；
   重启后验证新学到内容也已预热，并检查画质变体、图像完整性、编译时间和 FrameWait。
   不能仅以同一次进程里第二遍变顺作为完成标准。未采集到的其他内容仍可能首次编译，
   应报告其覆盖缺口而非宣称全游戏已消除。

### 0.57.7 模型到绘制提交的原生路径

针对 0.57.6 五段演示中剩余的 451 个 CPU 慢帧，本轮把所有普通模型和按绘制通道
过滤的模型接入完整的原生网格提交。不是只替换另一个状态设置助手，也没有把动画、
AI、碰撞或特效算法一并重写。

|边界|本轮实现|
|---|---|
|`003078B0` / `00307A10`|模型 LOD、世界矩阵、网格遍历、通道过滤、命令链连接与恢复|
|`0030BCA0`|完整网格提交：透明度、材质/纹理、前后效果回调、纹理层清理和绘制|
|`0030C240`|材质命令链遍历；`0030C2A0` / `0030C370` 等效果叶子函数仍调用原实现|
|HLE → threaded recorder|传递已准备的状态及变化范围，复用同一模型中的同步结果|

`00307B80` 单部件模型的外层暂保留，但它调用的 `0030BCA0` 同样走新路径。
没有减少模型、网格、特效或模拟次数，也没有调整分辨率、画质及限帧策略。

两个参考项目仍是 `black-pc` c065917 和 `ngb-pc-native-port` 94bc250。
两个项目的 `loader/src/d3d/draw.cpp` 都通过 `on_change` 避免重复设置相同状态；
port 还在纹理/矩阵等边界只向 D3D9
发送变化值，并明确在设备重置或其他路径改变状态时失效。这里采用相同的减少重复
提交原则，针对 ARM 重编译和异步渲染边界实现自己的状态所有权，不能直接照搬 PC
调用次数的收益。

第一次绘制仍完整同步；之后仅在同一原生模型、没有进入未知游戏代码时复用状态。
中断、DPC、协作式线程切换和游戏效果回调都会暂停模型所有权，返回后重新同步。
所有权令牌保存在当前宿主/协作线程栈上，避免另一条线程或嵌套回调继承外层模型。
已变化的简单状态、绑定、矩阵和材质范围直接告知 recorder；普通 Draw/Clear 会断开
版本链。资源头仅在同一录制批次且没有绑定变化时复用，换批次仍登记资源生命周期，
UP 顶点和索引捕获继续执行。索引快照、等待和资源释放语义不变。

简单状态的固定编码关系在每次设备创建后建立一次反向索引，保留同一编码对应多个
状态的情况。`NativeSimple` 不再为每次赋值扫描全部 92 项；绘制前的 `SyncDeferred`
也直接使用预先选出的有效简单状态列表。XBE 段标志验证了编码表位于只读区，生成
代码中对该表的直接引用都是读取。顶点缓冲及步长没有变化时，不再额外把整个绑定
范围标成已变。A/B 控制组保留原来的两种扫描过程。

旧 PGO 函数体保留，A/B 对照用汇编入口分支直接选择。反向还原两处材质助手的
6 个调用目标以及三个入口的标签、类型和大小声明后，汇编必须逐字一致。材质助手
用模板区分旧路径与已准备路径，避免对照组承担新增的逐项变化标记。A 仍有很小的
