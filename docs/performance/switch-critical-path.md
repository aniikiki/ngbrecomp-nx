# 重战斗：哪些工作应该从游戏线程移走？

最新真机 0.51.0-rc1，场景翻转 1801–1920：44.37 ms/帧，游戏线程 43.48 ms、GPU 5.98 ms（两者重叠）。目标是实机 16.67 ms/帧。下文用宿主 ARM 对比实现，不把两台机器的毫秒互相换算。

## 原样绘制时的游戏线程成本

用 0.51.0 候选包的游戏对象跑过 1920 帧。保持所有绘制及可见性查询，在重战斗的 80,683 次绘制中随机选中 10,119 次；每次只测一个范围，使用线程 CPU 时钟，并用抽到的空范围校正读取成本。每项约 1,000 个样本；相邻八帧为一块进行重抽样。范围有包含关系，不能逐行相加。

|120 帧的主机估算|ms/帧|重抽样区间|
|---|---:|---:|
|从高层 Draw 入口到返回，包括下面各项|0.558|0.520–0.596|
|从游戏内存同步绘制状态|0.128|0.115–0.141|
|记录状态（SendState），包括资源头和固定状态|0.296|0.274–0.317|
|资源头检查和记录|0.109|0.087–0.130|
|固定状态比较和记录|0.185|0.155–0.212|
|绘制命令、索引及批次提交的尾段|0.129|0.100–0.154|

这不包括上层游戏模型遍历、Draw 前的 XDK 函数或另一线程的 Vulkan 渲染。整段删除普通绘制的实验在重战斗看起来省了 2.6 ms，但是两组每帧函数入口相差超过 2 万次，且一部分场景翻转对应零次或约两帧的高层 Draw。那个差额包含时序、同步和工作量变化，不能算成可转移的绘制成本。

独立实现了保留画面的对照：每次将完整有效状态打包，消费者解包，免去逐字段找差异。680 次左右绘制的相邻重战斗帧，游戏线程 5.367 → 5.506 ms，省时区间 −0.261 至 −0.005 ms，故不采用。只改变状态传递尚未显示出足够大的收益。

## 四个任务之间传递了什么

在 47 个生成的 ARM 游戏编译单元中记录实际内存读写：只有实际改变一个字节的写，才成为该字节的新生产者。跨线程/纤程切换恢复归属；内核回调另外归类。观察 1801–1805 帧，完整回放到 1920 帧。下列是**读取次数按字节计**，重复读取会累计，不是唯一字节数或耗时。

|生产者 → 同帧消费者|改变后读取，平均每帧|最常见的路径|
|---|---:|---|
|更新 1CB9A0 → 渲染列表 1CA790|23,126|行矩阵运算 ngb_arm_x87_row → 37A5C5，占 48.9%；有序树构建 → 遍历，占 9.2%|
|更新 151150 → 更新 1CB9A0|1,105|13BEC0 → 305950 的矩阵取用，占 87.7%|
|渲染列表 1CA790 → 其他执行区间|79|以矩阵状态为主|

只插桩十四个热点单元时，第一条边是 10,673，且没有识别出首要的矩阵路径。不能把局部统计当成完整依赖图。当前覆盖了 47 个游戏代码单元，但部分宿主服务、编译器内联汇编、库复制仍不在观察范围内。任务跨帧、GPU 命令/读回和副作用也不能从这一张同帧表推出。可以确定的是，直接乱序执行四个完整回调会忽略真实的更新结果。

## 已排除的小改动

- 碰撞骨骼复用对至少 122,880 次采样检查了原版的寄存器和内存结果；重战斗 6.396 → 6.298 ms，差值区间跨零。
- 碰撞节点按程序原有的中断时机成批排除，支持此次游戏实际使用的高地址物理别名；至少 237,568 次批次边界与原版一致，重战斗 6.231 → 6.174 ms，差值区间 −0.127 至 0.285 ms。
- 多指针合并 RAM 检查在这次重战斗没有测出收益。以上均未进入 Switch 包。

原始离线日志在本地私有的 build/switch-runtime/opt048。记录成本用 record-single.log；保留绘制的整帧对照用 live-packets.log；全部游戏单元依赖用 task-flow-all.log。完整可玩的候选包仍见 [0.51.0 记录](switch-0.51.md)。

另一次完整 47 单元回放，在渲染列表首次恢复时保存 RAM 供离线比较。1802–1805 四帧，渲染自身尚未产生的输入有 82,175–108,790 个不同字节；其中 104–3,551 个后来读取的值与首次恢复时的快照不同。程序在这四帧中分别 75、25、22、43 次从其他执行区间返回渲染任务。1801 帧没有进入该任务，未混入范围。时间密集的插桩会扰动调度；这些数据证明整段渲染不能简单地用开始时的一份内存快照代跑，不是实机任务交错次数。

## ARM 指令路径（不同于 CPU 时间）

只在四个场景帧追踪宿主游戏线程实际执行的 ARM 基本块，通过后续第 1920 帧。取后两个帧，在与 Switch ELF 同名且大小一致的函数里映射指令位置。重型追踪显著改变音频线程的工作量；例如音频函数 3433F0 在跟踪中占匹配指令的 25.2%，但普通离线定时采样中只占 0.9%。不把指令占比当成周期或正常帧耗时。

在所选私有 ARM 寄存器函数、入口检查与跳板中，两帧约 5,063 万条动态指令，约 279 万条是从 x27 指向的表读取页面长度。普通路径还会取页内偏移、加访问宽度、比较、本机基址加法。这些操作散布在模型提交及游戏更新中，值得作为跨函数的优化对象。

用前两帧训练了完整函数的邻接顺序，实际重链接 Switch ELF 并验证 1,374 个函数按指定顺序落位。相同指令在后两帧的 48 KiB、三路、64 字节行 LRU 模型中，原版 / 重链接的缺失为 468,678 / 449,317 和 453,214 / 435,140，约减少 4%。仅模拟能够映射的游戏代码，不含其他函数的竞争、指令预取和真实硬件替换策略。未因此发布新包，不能把 4% 当作帧率提升。

在旧版 0.43 的同一真机窗口，按第 1800 和 1920 帧对应的累计计时相减，状态同步为 1.59 ms/帧，命令记录为 4.96 ms/帧。二者共 6.55 ms，且属于带分项探针的旧版；即使假设全部省掉，也填不上该版离 60 FPS 的 33.86 ms 差额。

## 直接访问 RAM 是否足够

- 两帧看到约 279 万次页长度读取，并不能说明删掉它们就会同比加速。十四个 ARM 编译单元改用主机基址表，保留精确慢路径：重战斗 4.721 → 4.789 ms。按地址训练并在访问时验证有效范围（保留原版后备路径），6.745 → 7.090 ms，省时区间跨零。
- 另在 Linux/AArch64 用稀疏地址视图，把十四个单元的 PUSH、POP 和部分显式栈/基址访问改为单条访存指令。只映射低地址时，一次完整回放有 477,859 次信号恢复，大多发生在高地址物理内存。让已分配且允许直接访问的高地址页映射到同一份物理存储，并保留每个物理块末页的保护，另一回放跑完 1920 帧没有发生一次恢复。开场仍从 3.830 增到 4.534 ms，重战斗 6.574 → 6.815 ms，节省区间 −0.607 至 0.145 ms。两组整帧工作量接近。这项替换也占用原本保存页表的 ARM 寄存器，并非免费；尚无依据将它移植进 Switch 内核接口。
- 在中断预算足够时，一次原生循环完成渲染排序树的一段递归插入。至少 133,120 个现场与原版核对了寄存器、栈、完整节点池、入口记录和轮询次数。重战斗 6.388 → 6.254 ms，差值区间 −0.543 至 0.780 ms。另一项把函数入口计数和轮询状态放在相邻内存、并让无需回调的入口不建栈帧，4.914 → 4.895 ms，区间 −0.049 至 0.084 ms。均未进入候选包。

相应原始窗口见私有日志 bias.log、site-range.log、stack-fault.log、stack-both.log、tree-shadow.log、tree-whole.log 和 checkpoint-state.log。

## 四个完整任务能否直接分配给四个核心

在 47 个游戏编译单元中，把同一角色的每次访存记为一个单位。模型允许角色之间无限并行，帧初的内存可直接取用；没有模拟 CPU、缓存、设备或调度成本。1801–1812 共十二帧，按字节保留读后写、写后读和写后写顺序时，各帧最长链合计 17,136,777 / 19,352,122 个单位（88.6%）。另一回放只保留改变过的字节被其他角色读取的依赖，最长链 16,700,826 / 18,820,169（88.7%）。两次插桩负载不同，接近的比例不能当作常数或实机时间比例。

后一回放的 80 次关键链跨角色衔接中，40 次经过 0x950180（当前矩阵），12 次经过 0xD52688（矩阵栈指针）；更新与渲染之间每帧都有一次经过 0x9777CC（材质状态缓存）。路径是从本次实际最长链反向追溯，绝非说矩阵乘法或某个四字节字段本身花掉了半帧时间。渲染线程以外已占用的核心也不能算作无限资源。

第三次回放在**同一次实际执行**中比较四种假设，单次访存仍只花一单位。若允许从历史中免费取到值相同的矩阵字节和栈顶指针，最长链总长度 15,589,095 → 14,741,571（−5.4%）。若任意地址只要与帧初值相同就可读取，−3.0%；若所有地址可免费取用任意以前的相同字节，−8.6%。后两者是故意宽松的理想模型，不能用来跳过实际游戏的同步；它们也没有计入维护版本的成本。不同回放因重型插桩触发额外客体工作，不比较跨回放的总事件数。结果支持改写任务内部的数据生成/消费，而不是将四个既有回调直接并发或仅复制当前矩阵。原始记录：task-path.log、task-chain.log、task-versions.log。

## 从关节变换前排除碰撞候选

离线从父函数取到的 79,218 份完整输入包含角色矩阵、骨骼矩阵、位置、边界和查询球。旧缓存只复用骨骼乘法；这次改为对整个包围体先建世界坐标范围，按每次查询球的半径在三个轴上扩张。在这批输入中，全部 79,218 次都能在原细查前判定不相交，逐次复算原六平面判定并核对原函数返回，均没有冲突。总共 18 种描述符，用 64 个槽、四路匹配时只重建 258 次。这段结果只覆盖捕获成功的输入。

独立的现场实验不修改游戏状态，在原游戏处理完候选后逐一核对返回值，完成完整 1920 帧。在这个父循环实际送来的至少 942,080 个候选中，世界范围测试全部判为不相交，原版逐个执行也全都返回零。这不是说该场景没有打中：其他列表、路径和函数仍能处理接触。不可据此删除原函数；矩阵、栈和中断可被后续游戏读取。下一层验证要在可安全跨过的轮询范围内合并整个无接触分支，并对照每一处可观察的状态与整帧时间。原始数据：opt049/pose/data、opt048/box-shadow.log。

完整替代单个候选的试验已实现：在六次轮询之内不会触发回调时，一次原生计算完成原来五次函数进入，并恢复原本的五条入口记录。两个独立回放（无缓存和加姿势缓存）分别至少核对 118,784 个完整现场，含寄存器、400 字节客体栈、当前矩阵、角色位置尾部、碰撞标志、入口环和中断计数，均通过第 1920 帧。首轮整帧 7.119 → 7.140 ms，区间跨零。单个调用被简化尚未在这轮测量中转化成整帧收益，未发布。另实现了将同一查询的连续未命中候选合并，只在下一次中断前提交，另行跑整组状态对照与整帧对照。

两种整组实现都完成 1920 帧，各自至少有 53,248 组在原代码上独立重走、逐字节核对通过，每组 2–9 个候选。早先的试验没有真正进入整组路径：实际查询对象位于调用者的栈帧（一次取样为 SP+128），不在本次写入区间。修正范围后，重战斗同场对照，世界包围盒版原版 8.043、合并版 8.222 ms；按局部平面拒绝版原版 7.917、合并版 8.111 ms。两次省时区间都跨零，且当时有并行离线任务。没有依据发布任一方案。日志：group-corrected、compact-corrected 及各自的 -ab。

## 同一循环中的不同角色能否并行

在固定的重战斗 12 帧，对两段原版循环的每次迭代按角色编号及循环归属追踪。读写只统计实际被插桩的 47 个游戏单元，忽略循环以外的耗时和写入，没有调度/复制成本。每次 RAM 操作等权；下表是各帧最长依赖链的合计，并非 CPU 周期。每个角色自身仍严格有序。仅对改变过值的写建立读后写依赖。私有空间的假设为当前 SP 以下 16 KiB 至 SP+4、当前矩阵及矩阵栈顶指针；不代表这些区域实际上都可私有化。

|原循环|每帧角色|操作总数|按实际字节依赖|忽略私有空间的跨角色依赖|角色之间完全无依赖|
|---|---:|---:|---:|---:|---:|
|1CC5F0（角色槽扫描及各部件处理）|64|927,126|882,723|812,197|230,410|
|147ECD（每角色三个更新调用）|11|1,879,425|1,838,759|972,131|380,697|

第一个循环即使私有化上述范围，仍留下 87.6% 的链长；第二个从 97.8% 降到 51.7%，更值得追查未私有化的输入输出。该实验在整场回放保留插桩入口，仅在观测窗口收集数据，避免一开始就已驻留的纤程绕过插桩入口。首轮仅在窗口内启用入口选择时未采到迭代，不作证据。原始日志：actor-resident.log。

再跑十二帧，保留每次跨角色依赖的指令位置，并从最长路径反向追溯。第一循环 93 次衔接全在 308BF0（有序树插入）内部，89 次为 954724 所在 16 字节块；原代码在此读取下一节点指针，再按 20 字节递增。第二循环则不同：72 次衔接中，60 次经过碰撞结果计数 7A6870，12 次经过碰撞标志 DB67C0。结果是三个不同实验的交点：一次单独的骨骼计算不够重，整组候选也没有可靠省时，而在角色级别，重复使用同一个碰撞结果累加器把本来可能独立的运算串在了一起。同值写回和真正从前一个角色读到不同结果要分开验证。这些比例都不是可直接省下的帧时间；原始数据 actor-joins.log，重现分析用 flow/actor-report.py。

另用同一次执行对“写入相同值”单独建模。每个角色自己的每条写即便没有改变字节，也定义了该角色随后可读取的值；若程序顺序更早则可作为较早的生产者。在已假设临时栈及矩阵私有的前提下，第二循环最长链下降到业务完全独立时的约 20.3%。这是可复核的并行化线索，不等于能省去 79.7% 整帧 CPU。进一步从循环起点保存内存，对每次迭代首次外部输入逐字节比较，先写后读不算外部输入。132 次迭代中，角色池 100,258 个输入字节全部相同，其他静态内存 40,246 个全部相同；两个碰撞字段没有先读再写。动态内存 409,453 字节仅 120 字节不同，全部来自同一客体栈页 011C7000（每个非首角色 1 字节），私有栈另有 1,332 / 2,172 字节不同。统计按每次迭代累计，不是全程唯一地址。尚未验证非插桩代码、在途回调或跨帧；不能据此并发运行共享全局状态的游戏代码。原始日志 actor-forward 与 actor-inputs。

另一条内存实验在十四个 ARM 单元将 51,563 处动态读取、43,182 处写入改成受页保护的直接访存，保留 x27 原页表。独立 ARM 测试通过四种宽度/浮点、共享物理别名、解除映射和跨页回退。完整回放注册 88,143 个故障恢复位置，首轮有 13,620 次恢复，两处物理地址段占全部故障。在独立训练回放按指令位置记下 8,164 次恢复，再将对应的 226 处直接跳回原已检查路径，第三次回放只剩 21 次恢复，仍跑完 1920 帧。重战斗整帧游戏线程 9.081 → 9.843 ms，省时区间 −1.675 至 0.108 ms。离线存在其他负载，未证实正收益，不进入 Switch 包。以上是 Linux 私有双映射实验，不需改变 Switch 权限。

分开跑正常 ARM 代码，用线程时钟只计循环体，遇实际纤程切换、内核回调时暂时转移计时归属。重战斗 120 帧：角色扫描 1CC5F0 为 0.297 ms/帧（该次游戏线程的 3.1%），排序后的 11 角色循环 147ECD 为 0.515 ms/帧（5.3%）；另一回放中后续遍历 149640 为 0.337 ms/帧（4.1%）。均为宿主常规寄存器版本，线程计时本身有开销，不能当作 Switch 毫秒。这也给并行化试验划出上限：一个 11 角色循环即便完全免费也解决不了整帧，若机制成立，需要复用到其他更新与提交阶段。日志 actor-clock、actor-stage2。

[真实角色工作线程的验证结果](switch-actor-worker.md)：从访问次数模型推进到 devkitA64 原函数在第二条 ARM 线程上运行；区分了可提前计算的结果、必须继承前一角色的栈输入，以及并行的交接成本。

另测原版物理 push buffer 的索引提交。游戏会在相同地址持续修改最后一个跳转字；解码缓存只可忽略已验证为终止跳转的目标值。实现一条复用已解码索引的路径和一条直接读取单段索引的路径。两者分开跑至第 1920 帧，均实际接手 5,697 / 5,697 次实验组命令；另用 50,000 份含地址复用、内容变更和多绘制的输入与独立解析器逐字节比较。两个重战斗整帧差值区间均跨零：缓存 6.037 → 5.722 ms，单段直读 5.446 → 5.370 ms。未进入发布包。原始数据为 push-tail 和 push-span。

## 角色交接与共享渲染路径的整帧验证

[角色并行的端到端对照](switch-actor-worker.md)已包括跨核等待。即使实际采用 280 项计算结果，交接成本仍超过收益。按渲染列表中的动态目标单独记账，又一次跑完重战斗。四个共享模型回调 1CB510、1CB260、1CB3B0、1CB550 在这次常规 ABI 回放中分别耗费 0.511、0.366、0.324、0.219 ms/帧，合计占整个游戏线程 24.6%。这包含原游戏逻辑、设备库调用和绘制提交，不是调用指令本身耗费四分之一帧。

把四个入口和共有的模型提交路径共 19 个函数编成一个 ARM 编译单元，保留原始绘制、设备钩子、轮询和所有对外调用。相邻重战斗帧 6.378 → 6.214 ms，省时区间 −0.223 至 0.525 ms，目前不能确认。独立试验让 67 个 D3D 入口从游戏的 ARM 调用约定直达原设备代码，再对八种常见状态直接传标量寄存器。标量版开场和中等场景有正差，重战斗 4.706 → 4.700 ms，区间 −0.083 至 0.090 ms。另将相同顶点程序、声明与地址完全相符的 SelectVertexShader 结果复用，独立回放 7,809 次命中与原重新构建的指令和声明一致；重战斗 5.521 → 5.658 ms，区间跨零。均未进入候选包。私有日志为 opt048/render-{callbacks,island,dispatch,light}、private-{d3d,scalar} 和 shader-{verify,pair}。不同实验的基线不能拼接计算提速。

对四个模型回调及其余游戏代码又做了两项独立的调用边界实验。按实际跨单元分支次数排序，将 ARM 寄存器直传范围从 14 个单元扩到 22 个，重战斗宿主游戏线程 5.452 → 5.315 ms，节省区间 −0.047 至 0.360 ms。另一项让内部间接调用在识别出已编译的 ARM 入口时保留私有寄存器，普通函数指针仍然走原约定，重战斗 6.064 → 5.986 ms，区间 −0.261 至 0.406 ms。两项都完成了 1,920 帧；都没有可靠依据替换现有包。

另外测了在没有外部调用的 SSE 指令段内统一检查普通内存范围、暂存寄存器：665 个函数有 2,240 个代码段符合条件，重战斗 9.125 → 9.077 ms，区间 −0.884 至 0.960 ms。单独关闭入口历史环的写入但保留当前函数、完整轮询和服务，重战斗 7.585 → 7.514 ms，区间同样跨零。保留正式版的故障日志。以上日志在 opt048/{extended-abi,paired-indirect,simd-spans,checkpoint-quiet}.log。存在并行离线负载，不跨次比较绝对值。

重新分类 407 个真机游戏线程样本：29 个在 DMA，21 个在其他轮询/服务，90 个在 D3D 拦截，57 个在其余模型提交/XDK 路径，43 个在排序渲染列表其余部分，167 个在普通游戏或其他代码。更新 0320E0 的 52 个栈中 17 个属于 DMA。分类依赖展开栈，是墙钟采样次数，不是确定周期。见 perf/device-runtime-split.py。
